<objective>
Close the record: name the root cause, propose the fix, and prove by git history that both predate
any fix.

Purpose: this is D-06's gate. PARITY-01's central claim is not "we found the cause" -- it is "we
found the cause and wrote it down BEFORE we changed anything", because every `nx.json` edit rotates
hashes and contaminates the investigation it would otherwise be documenting. The record is complete
at this plan's last commit, and the next commit in the phase is the first fix commit.

Output: the record's `## Root cause`, `## Proposed fix`, `## Hand-off to Phase 12 (DOCS-07)` and
`## Requirement coverage` sections, plus a git-history audit proving the ordering.

HARD ORDERING CONSTRAINT (D-06 / D-15): no commit in this plan may touch `nx.json`. This is the LAST
plan in the phase for which that holds, and task 2 is where it is proven for all four.

Why the fix is PROPOSED here rather than applied here: writing the route down before taking it is
what keeps the fix from being reverse-justified. If the fix landed first and the record were written
after, "we changed X and the hashes agreed" is indistinguishable from "we changed X, Y also changed,
and we attributed the result to X".
</objective>

STEP 1 -- write `## Root cause`.

This section answers PARITY-01 and it must be derived from what plan 08-03 measured, not from what

have in common and what they do not.

For the OS axis: name what the cross-OS diff produced, leading with the bucket it actually produced.
The two buckets imply DIFFERENT fix routes and this distinction is the section's whole point:
- entries in `only-in-A` / `only-in-B` mean the two legs saw a different SET of external dependency
  nodes -- the shape a platform-conditional optional package set takes -- and the route is to
  NARROW the affected target's declared external dependencies;
- a `value-changed` entry on the merged project configuration node means inference produced a
  different merged node on the two operating systems, and the route is a `targetDefaults` entry that
  normalises the differing field regardless of what inference produced.
Both may be present. Name every one that is.

Where `08-RESEARCH.md` offered a prediction, quote it beside the measurement so the divergence or
its absence is visible. Its Finding 3 names a Windows separator sensitivity in `@nx/js/typescript`'s

STEP 2 -- write `## Proposed fix`.

Constraints, stated at the top of the section so the proposal is visibly bounded rather than
apparently free: fixes land in `nx.json` `targetDefaults` only (D-12); no `project.json`, because
this workspace is deliberately free of them; no plugin-option patching as a first resort; narrowing
inputs is preferred over adding them (D-13); and `integration`'s runtime discriminator stays
BYTE-IDENTICAL -- Phase 8 does not re-spell it, it only asserts it is the only one, because after
VER-03 it is the sole mechanism separating OS-sensitive targets and touching it is a Core-Value
regression (D-14, CORR-04).

Then, for each diverging node the root-cause section named, propose a specific route by NAMING THE
KEY. For a merged-project-configuration divergence localised to the inferred `typecheck` outputs,
the route is a `targetDefaults.typecheck.outputs` entry, and the evidence that it will work is
already in the record: `nx.json` declares `targetDefaults.typecheck.inputs` today, and the `inputs`
field of the merged node is identical across states while `outputs` is not -- a live, in-repo
demonstration that a `targetDefaults` entry normalises ITS field of the merged node regardless of
what inference produced. State that this is a hypothesis with a named, cheap confirming experiment
and not a conclusion.

State which VALUE that entry must carry, citing the enumeration plan 08-03 produced rather than
either candidate list's size. `outputs` is load-bearing beyond the hash: it is what Nx caches and
restores, so pinning a list that is merely STABLE rather than CORRECT would silently stop
`typecheck` caching its declaration output -- which is a correctness regression in the very cache
this project exists to make trustworthy.

For an external-dependency-set divergence, propose narrowing the affected target's declared
`externalDependencies` and name the target and the packages, noting that all five targets already
declare an `externalDependencies` entry so the route is an edit rather than an addition.

Note that `nx.json` is strict JSON and carries no comments, so each proposed fix's rationale lock
must live in the guard spec that pins it (D-13). Name that spec:
`packages/github-cache/src/nx-target-inputs.spec.ts`, which already carries exactly this pattern for
`targetDefaults.lint.outputs` -- the value in `nx.json`, the comment explaining WHY that value in
the spec at :229-234 -- and which is already protected from a stale cached PASS because
`{workspaceRoot}/nx.json` is a declared `test` input, asserted in that same file at :269-273. State
that the pin must EXTEND that file rather than being re-authored elsewhere, because re-authoring
creates a second copy to drift.

STEP 3 -- write `## U-01: the condition that would make it live`, and write it BEFORE the experiment

- what outcome would CONFIRM the proposal (the diverging node stops moving after the proposed

- what outcome would make U-01 LIVE (the node still moves, or the divergence is in something
  `targetDefaults` cannot reach -- inference internals, a plugin option, or the plugin's own path
  handling);
- and that in the live case plan 08-05 STOPS and re-opens the fix location with the maintainer
  rather than improvising one. The options that open up are named in U-01 itself: pinning the
  inferred target explicitly, patching plugin options, or escalating upstream.
Add one sentence stating why upstream reporting of the plugin behaviour, if the measurement supports

STEP 4 -- write `## Hand-off to Phase 12 (DOCS-07)`.

DOCS-07's portability checklist is deferred to Phase 12 and its items are DERIVED from this record,

  directories, as the non-destructive alternative for anyone reproducing the measurement.

Do NOT touch `nx.json`. Do NOT apply any fix in this plan. Commit the record.
