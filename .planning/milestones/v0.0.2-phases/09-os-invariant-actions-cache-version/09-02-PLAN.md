SECTION 1 -- `## The prediction`. State, as a claim that can be checked against one specific job
summary rather than as a mood:

Say explicitly that a `scanned` of 0 does NOT satisfy the prediction: the warning's branch requires
`hashes.length > 0`, so a run that enumerated nothing is a different event and must not be read as
this one.

SECTION 2 -- `## The axis, and why naming it matters`. The mechanism here is the `@actions/cache`
CACHE VERSION -- the sha256 of the literal archive path strings plus the compression method plus the
conditional `windows-only` component. Reproduce the three-window table with a MECHANISM column and an
AXIS column:

| Window | Phase | Mechanism | Axis |
|---|---|---|---|
| 1 | 7 | the inferred `lint` target changes `hash_project_config`, and `nx.json` is itself a `test` input so `test` rotates twice over | Nx TASK hash |
| 2 | 9 | the archive-path literal changes `getCacheVersion`'s input | `@actions/cache` cache VERSION |
| 3 | 10 | the Releases asset name changes (CORR-02) | Release ASSET NAME |

Then state the consequence in one sentence: a tripwire keyed on "all-restore-MISS at publish" sees
window 2 directly, while windows 1 and 3 produce a superficially similar all-MISS through unrelated
machinery -- so any message or note that says only "rotation" lets a reader misdiagnose the other
two, and D-30 forbids authoring a tripwire that fires on them.

SECTION 3 -- `## Attribution: the PATH, not the flag`. The both-legs all-MISS is caused by VER-01's
path change. `enableCrossOsArchive` alone rotates ONLY Windows entries, because `cacheUtils.js:166`
pushes the `windows-only` component only when `process.platform === 'win32' && !enableCrossOsArchive`
-- so on Linux and macOS the flag is a no-op on the version. Record the corollary as a diagnostic:
an asymmetric signal (Windows leg all-MISS, ubuntu leg normal) would mean the flag landed WITHOUT the
path, which reads like a Windows-specific breakage and is not this event.

SECTION 4 -- `## The version-affecting commits in this phase`. Exactly ONE: plan 09-03's commit,
which lands VER-07, VER-01, VER-02, VER-03 and VER-04 together plus the rebuilt
`start-cache-server/index.js`. Name the two reasons that merge is load-bearing rather than tidy: VER-01
and VER-03 EACH change `getCacheVersion`'s input, so splitting them would give the milestone FOUR
rotation windows where D-30 says three and this record says "once"; and a VER-03-only commit produces
the asymmetric Windows-only signal of Section 3.

Then add the explicit maintenance instruction: if that commit is ever split, THIS FILE must be
rewritten to enumerate every version-affecting commit rather than leave "once" standing. Do not leave
a reader to infer it.

Also record the bundle coupling, because it produces a signal that LOOKS like this one: if a
`serve()`-reachable edit ever reaches `main` WITHOUT the rebuilt bundle, the five sidecar sites write
at the old version while the publish action restores at the new one, and the mirror silently stops
receiving -- surfacing as exactly this all-MISS warning, on a run where it is a DEFECT.
`action-bundle-drift` catches it, but only after the misleading signal has been rationalised. That is
the single most likely way this record gets misused.

SECTION 5 -- `## The tripwire`. State the gate verbatim as OBS-04 requires: **two consecutive
all-miss pushes with NO version-affecting change in between**, not a raw push counter. State that it
is a documented READING INSTRUCTION, carried in this record and in the warning message itself, and
that it stays a `core.warning` -- never a hard failure, because a tripwire that fires on correct work
gets disabled and then it is not a tripwire.

Enumerate the rejected alternatives with the reason, so a later maintainer does not re-litigate them
silently: a persisted marker (a Release asset, a repo variable, a cache entry) and a scheduled job
diffing the last two runs. Both add mutable observability state, which this project's Key Decisions
already reject on principle (the LRU-manifest row: "a manifest adds mutable retention state
(security-negative)"), and OBS-04 itself says the mechanism stays a warning. Note that adding a
mechanism later is strictly additive -- one warning message, no contract frozen.

SECTION 6 -- `## Non-triggers`. Phase 8's discipline: the half that does the work. At minimum, state
that NONE of the following is this signal, and say what each one is instead:

- an all-MISS push whose commit range contains no change to `cache-archive-path.ts` or
  `actions-cache-backend.ts` -- that is the tripwire FIRING, and the reader must act;
- a single-leg all-MISS -- see Section 3;
- an all-MISS following Phase 7's `lint`-inference commit or Phase 10's CORR-02 rename -- windows 1
  and 3, different axes;
- a `scanned == 0` run -- the warning's branch is unreachable there;
- an all-MISS with `failed > 0` -- that run already failed loud through `core.setFailed`, so it is a
  mirror fault, not a rotation.

SECTION 7 -- `## How this record is consumed`. Two lines: it is read at the first `main` push after
the merge (a `human_needed` item this phase closes with, per H5 -- the push filter at `ci.yml:3-7`
plus `publish`'s `if: github.event_name == 'push'` mean nothing on this branch or on a PR can produce
it), and its axis wording must MATCH plan 09-06's reworded warning message.

Do NOT edit `publish-mirror.ts`, `publish-mirror.spec.ts`, `ci.yml`, or any source file in this plan.
