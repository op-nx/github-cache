**Structured corroborator, explicitly secondary (RESEARCH.md's `run.json` finding):**
the set of `tasks[].target` values in `.nx/cache/run.json` whose `cacheStatus` equals the exact
string `remote-cache-hit` is expected to be exactly `{build, typecheck, test, integration}`, four
members. Under the failure hypothesis every one of them reads `cache-miss`. This field discriminates
remote from local, which is precisely what the `Cache: n/m hit` line cannot do.

**Corroborator, explicitly secondary:** the run-duration collapse. Step 0 measured a 1 ms replay
against a real 554 ms execution, and `10-EVIDENCE-PRE-RENAME.md` recorded 961 ms for a real
`integration` run and 2.4 s for a real four-target run. A four-target run served from the remote
should be far below the 2.4 s all-miss figure.

**NON-DISCRIMINATING IN BOTH DIRECTIONS, and it must be labelled so beside the line (D-24):**
the `Cache: n/m hit` line. Measured grounds: a `0%` prints identically with no sidecar at all (run
`30169158892`), and a non-zero count includes LOCAL hits. Nx 23.1's end-of-run performance report is
supporting context only.

## Anti-requirements -- what explicitly does NOT count

Each is a success criterion stated in the negative, and each is worth restating because a tired
reader would accept it.

- A HIT recorded without a preceding reset. A local cache hit short-circuits before the remote is
  ever queried, and `.nx/cache` on this box held an entry for the `test` hash before plan 11-02's
  reset, so this is a live hazard rather than a theoretical one (TEST-10).
- A `Cache: n/m hit` line read as discriminating, in either direction (OBS-02, TEST-10, D-24).
- A producing-OS reading of `mirrored-by`. `10-EVIDENCE-LIVE-CI.md` records the Windows-produced
  `integration` hash stamped `mirrored-by: linux`, live (D-14).
- A "the run was green" claim with no paired count (TEST-08).
- Re-deriving `H_linux != H_win` here. That is O3's, and it is CITED in plan 11-07, never re-derived.
- Answering PARITY-04's "does my everyday box hit". The reset forces the COLD state, so this session
  answers the cold question only. Say which question each proof answers.

## THE HARD ORDERING RULE, carried from plan 11-02

Between plan 11-02's `npx nx reset` and task 2's measurement run, the ONLY permitted `nx` invocation
is task 2's own `nx run-many`. No verification run, no `nx test`, no `nx build`, no `nx show`, no
`nx format:check`. Any of them repopulates `.nx/workspace-data` and writes into `.nx/cache`, and a
`test` entry written by a verification run turns O1's `test` remote hit into a local hit that proves
nothing. VALIDATION.md's after-every-task-commit sampling is SUSPENDED for tasks 1 and 2 and
resumes at plan 11-05.

Do NOT run a build before the measurement either. `packages/github-cache/dist/` survives `nx reset`
(verified in Nx source), and a rebuild would repopulate outputs that `typecheck`'s
`dependentTasksOutputFiles` input hashes, which is the one thing that could move a proof target's
hash mid-session.
