## Two design choices recorded rather than taken silently

**1. The `runner.debug` recorder is ECHO-ONLY, not a fatal gate. This deviates from RESEARCH.md's
recommendation, and here are the reasons.**

RESEARCH.md recommends a step that `exit 1`s when `runner.debug` is not `1`, plus a pre-registered
removal. Taking the echo-only form instead, for three reasons:

- A fatal gate becomes a PERMANENT tripwire that reddens every run once the
  `ACTIONS_STEP_DEBUG` variable is unset after the proving run. This file's own `publish` job records
  the rule: a tripwire that fires on correct work gets disabled, and OBS-04 is this repo's own record
  of that happening.
- Add-then-remove needs a follow-up `ci.yml` edit whose only purpose is undoing this phase's edit,
  and it needs the removal to be kept OUT of plan 11-05's phrase locks or the removal reddens a lock.
  That is two coupled edits and one guard-shaped trap for one run's benefit.
- The reason RESEARCH wanted the gate, failing DURING the run so a run is not wasted, is recovered by
  plan 11-07's two read-only pre-flight commands: one proving no overriding `ACTIONS_STEP_DEBUG`
  SECRET exists, one proving the VARIABLE is set. Both run BEFORE the push, so the configuration is
  verified before a run is spent.

The echo keeps RESEARCH's other two reasons intact in full: it produces the line that goes straight
into `11-EVIDENCE.md` as a recorded fact, and it observes the EFFECT rather than the configuration,
so it is immune to the secret-takes-precedence trap. It is permanent, costs nothing, and makes every
future run self-document its debug state.

No `DOCS_08_SITES` row locks the debug recorder's prose, so it remains freely removable if it ever
stops being wanted.

**2. The `o3-witness` job does NOT check out the repository.** It needs no repo file: it is `curl`
plus `jq` against two REST endpoints. `hash-parity-compare` checks out and builds because its
comparator is TypeScript in `dist/`; this job has no comparator to build. `contents: read` is still
RESTATED in the job-level `permissions` block, because such a block REPLACES the workflow grant
wholesale rather than merging it, and the honest comment says both things: the restatement keeps the
job's grant from silently narrowing the workflow's, and the job needs no repo content today.
