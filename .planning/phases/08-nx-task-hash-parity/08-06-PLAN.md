Add a `hash-parity-compare` job to `.github/workflows/ci.yml`, positioned immediately after the
`hash-parity` capture job it consumes.

SHAPE:
- `needs` the capture matrix job.
- An `if:` expression that still runs when an upstream leg FAILED or was SKIPPED. This is D-17's
  actual requirement and it is what makes "fewer than two records is a FAILURE, not a skip"
  reachable at all -- a dead leg still has to arrive at the assertion. D-17 names the
  always-running form; RESEARCH notes the not-cancelled form is narrower while still covering
  failure and skip, and this repo ALREADY prefers the narrower one on a dependent job (`publish` at
  :641 uses exactly it). Choose the narrower form, and state in the comment that it is chosen
  deliberately as satisfying D-17's intent while matching house style, not by reflex -- a cancelled
  run producing a red compare job is noise, and cancellation is the only case the two forms differ
  on.
- A single ubuntu runner. This job compares two records; it is not per-OS. Note in the comment that
  this is the FIRST job in the file that collapses a matrix's legs into one downstream job that sees
  both -- every existing `needs` either fans in from a single job or is itself a matrix pairing up
  leg-by-leg -- so a reader looking for a precedent should find that sentence instead of going
  looking.
- `timeout-minutes` matching the sibling jobs.
- NO job-level `permissions` block: `ci.yml:658-661` records that such a block REPLACES the
  workflow grant wholesale rather than merging, and the workflow-level `contents: read` covers
  checkout plus an artifact download.
- NO event gate. Every job in this file carrying a push gate does so because it WRITES; this one
  only reads and asserts.
- NO `continue-on-error` and no advisory-first period (D-18). This is build-gating from its first
  commit.

STEPS, in order:
1. checkout, setup-node with the node-version file and the npm cache, `npm ci`.
2. `npm run build`. This is mandatory and easy to forget: the comparator is TypeScript, so the built
   bin does not exist until this step runs. `pack-check` at :121-131 and `publish-verify` at :749-765
   both carry the same build-then-run ordering, and `pack-check`'s comment at :119-120 states the
   reason.
3. Create the records directory before the download, so the loader always has a directory to read
   even when nothing arrived. Note the residual limitation in the comment: if the download action
   itself errors on a zero-match pattern, the job is still red but the blame lands one step earlier
   than the comparator's named `wrong-record-count` reason. That is an accepted, recorded
   limitation -- the fixture case for that clause is unit-proven regardless.
4. `actions/download-artifact` at its current major, with a `pattern` matching the capture job's
   per-leg artifact names, `merge-multiple` enabled, and the records directory as the path.
5. A named, `shell: bash` step with `set -euo pipefail` that runs the built comparator bin against
   the records directory, tees its combined output to a log, and then greps that log for the
   loader's stable success prefix.

That last step's grep is the D-23 half and it is not optional. The pipeline's failure mode is the
first half -- a non-zero exit from the bin fails the step under `pipefail` -- and the grep is the
second: it asserts the comparison actually RAN and printed its verdict, rather than the step
succeeding because the bin was absent, the records directory was empty in a way the loader tolerated,
or a future refactor turned the assertion into a no-op. The `lint` job at :66-72 is the exact
precedent, and Phase 7's measurement that a run-many over a missing target exits 0 is why the
precedent exists. If the printed line is ever derived from Nx output, the colour-suppressing env var
becomes load-bearing too; the loader's prefix is deliberately plain, so state that it is and why.

Do NOT derive this job's verdict from the upstream jobs' results. D-23 is explicit that the record
FILES are the evidence and the job results are not: a leg can succeed and still have written a
truncated record, and a leg can fail after a valid upload. The `if:` expression governs whether this
job RUNS; nothing in it may govern whether this job PASSES.

Do NOT write any spec asserting on `ci.yml` content. `nx.json` lists `cleanup.yml` and not `ci.yml`
among the `test` inputs, so such a spec serves a stale cached PASS; registering `ci.yml` is
PARITY-08 in Phase 9. The job's comment block is the only place this rationale can live, which is
why it carries so much of it.

Wire the `lint` clause per plan 08-05's verdict. If `lint` came back identical across the legs, no
workflow change is needed -- the comparator already asserts it as the fourth invariant target. If
`lint` DIVERGED and the fix proved out of scope, apply D-21's named fallback: the clause is
DOWNGRADED, never deleted, which means the comparator keeps a named test recording the finding and
the record names it. Never remove the clause and never quietly move `lint` out of the invariant
list without a test that says so by name.

Push and confirm the job runs GREEN at the current commit. A green run is necessary and not
sufficient -- task 2 is where it becomes evidence.
