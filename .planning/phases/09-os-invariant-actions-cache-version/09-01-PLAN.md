<objective>
Register `ci.yml` as a `test` input, and prove the registration survives the configuration Nx actually
hashes.

Purpose: two later plans in this phase assert on `ci.yml` content. `nx.json` lists `cleanup.yml` and
NOT `ci.yml`, so until this lands every one of those assertions serves a stale cached PASS -- the
same false-pass class this repo has already shipped twice (`governance-email.spec.ts`, and
`typecheck`'s spec-excluding inputs). This is why PARITY-08 is FIRST in the phase and not a tidy-up
at the end.

Output: one entry in `nx.json`, and a three-clause guard in `nx-target-inputs.spec.ts` carrying the
comment lock that strict JSON cannot hold.

Vertical slice: one behavioural property (a `ci.yml` edit invalidates `test`) closed end-to-end --
the config entry, the guard that pins it, and the negative control that proves the guard is not
vacuous. No `serve()`-reachable file is touched, so this plan carries no bundle obligation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `nx.json` input list -> what `test` actually hashes | A missing input makes a spec's PASS a replay of a computation taken before its subject existed. The verdict looks identical to a real pass. |
| `nx.json` `targetDefaults` -> `project.json` | A lower-precedence-looking file sits HIGHER in Nx's merge for `inputs` and can replace the list wholesale. A guard reading only `nx.json` cannot see it. |
| Guard result -> reviewer confidence | A green guard is the only signal a reviewer gets that the registration is live. A vacuous guard converts an open hole into apparent coverage. |

The entry becomes effective on its own commit, because `{workspaceRoot}/nx.json` is already a `test` input -- there is no window in which a later spec replays a pre-registration pass. |
