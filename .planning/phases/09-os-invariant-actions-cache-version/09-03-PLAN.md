<objective>
The cache version stops depending on which OS computed it, in one commit.

Purpose: `@actions/cache` sha256s the raw archive path strings into the cache version, so a
per-OS temp path and a `windows-only` salt are the two things keeping a Linux-written entry
unreadable from Windows. Both go here: the path becomes a workspace-relative forward-slash literal,
`enableCrossOsArchive: true` is hardcoded at all three call sites, the directory the literal names is
created before the first write, and a construction-time guard makes the cwd /`GITHUB_WORKSPACE`
identity enforced rather than assumed.

Output: one commit containing the two production edits, the replaced and extended specs, the
three-file spec accommodation, the CORR-05 row removal, and the regenerated action bundle.

**ONE COMMIT, and it is a hard constraint, not a preference.** VER-01 and VER-03 EACH change
`getCacheVersion`'s input. Split, they give the milestone FOUR all-MISS rotation windows where D-30
says three and plan 09-02's record says "expected once". A VER-07-only commit creates a `mkdirSync`
for a path nothing writes yet. A VER-03-only commit rotates only WINDOWS entries
(`cacheUtils.js:166`), producing an asymmetric signal that reads as a Windows breakage rather than a
rotation. And VER-04's guard without its spec accommodation is a red tree.

So: Task 1 writes the specs and is EXPECTED to be RED. Task 2 makes it GREEN. Task 3 proves the new
assertions can fail, then commits ONCE. **Do not commit at the end of Task 1 or Task 2.**

Vertical slice: one behavioural property (the version is OS-invariant) closed end-to-end -- the
production code, every guard that pins it, and the bundle rebuild that makes the sidecar agree with
the publisher. A slice that landed the code without its guard, or the source edit without the
regenerated bundle, would be a horizontal layer in disguise.
</objective>
