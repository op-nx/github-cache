<design>
## The shape, and what it can and cannot catch

### The change

`read-back.ts` currently asks "do these bytes equal MY OS's payload?". It will ask "do these
bytes equal a KNOWN producer's payload for THIS hash, and which one?":

```ts
const producerOs = CACHE_OS_VALUES.find((os) =>
  result.bytes.equals(dogfoodBody(hash, os)),
);

if (producerOs === undefined) {
  throw new Error(/* widened message, see Task 2 */);
}
```

`CACHE_OS_VALUES` (`lib/release-asset-name.ts:8`) is the existing runtime tuple the `CacheOs`
type derives from and `isServerProducedAssetName` already validates against. `.find` over a
`readonly ['windows','macos','linux']` narrows to `CacheOs | undefined` with no cast. The import
swaps `cachePlatform` for `CACHE_OS_VALUES` from the SAME module -- no new dependency edge, and
the last ambient platform read in the comparison goes away rather than moving.

### Why not an extracted pure module

`hash-parity/compare.ts` + `assert-parity.ts` is the repo's split-the-decision-out precedent,
and `compare.ts`'s own doc block gives the reason it exists: it is "the only location where it is
typechecked and unit-testable", because the instrument it serves is an untyped root `.mjs`. That
reason does NOT transfer -- `read-back.ts` is already typechecked and already importable. The
repo's other two bins (`cleanup/index.ts`, `action/index.ts`) both export `run` behind the same
`isEntrypoint` guard and are driven by a co-located spec. Following THAT pattern makes the
decision testable through the real wiring with no new module for a `.find()`.

ponytail: skipped a `read-back-provenance.ts` leaf; the decision is one `.find` and the
bin-exports-`run` pattern already exists twice in this package. Add the leaf only if a second
caller ever needs the same recognition.

ponytail: skipped a source-text drift guard asserting the same-OS phrase is absent from
`read-back.ts`. The behavioural `it.each` over all three producers already reddens on any
same-OS regression -- test-enforced beats a second, weaker text scan of the same fact.

### What the guard CAN still catch

| Failure class | Why it still fails |
|---|---|
| Garbage bytes | No `CACHE_OS_VALUES` member produces them -- `.find` returns `undefined`, throw. |
| Partial / truncated upload | `Buffer.equals` compares LENGTH first, so a prefix of the right payload matches nothing. |
| An asset for a DIFFERENT hash | `hash` is folded into the payload bytes (`dogfood-body.ts:41`), so a different hash matches no candidate -- including a same-LENGTH neighbouring run id. |
| A cross-run asset-name collision | Same mechanism: a different run supplies a different hash, so the collided asset's bytes match no candidate for THIS hash. |
| A real cache archive resolved by mistake (a `.tar`) | Not a dogfood payload at any producer OS -- throw. |
| A MISS (asset absent, wrong shard, reader fault swallowed) | Unchanged -- the `kind !== 'hit'` branch above is untouched. |

### What the guard can NO LONGER catch

**A publishing leg mirroring the OTHER leg's payload under its own asset name.** That is exactly
the situation that is now LEGITIMATE and expected: both `publish` legs share one run-scoped seed
key (`nx-cache-<GITHUB_RUN_ID>`), so whichever leg restores it mirrors those bytes under its own
`<hash>-<os>` name. After this change the reader RECORDS which OS produced the bytes and does
not judge it.

Consequence, stated plainly: a Windows publish path that is entirely dead can no longer be
detected by this job, because the ubuntu-produced payload it mirrors is accepted. **That
detection is ROADMAP Phase 10 item 3 / OBS-05** ("each `publish` matrix leg seeds a
leg-DISTINGUISHABLE hash and each `publish-verify` leg reads back its OWN leg's asset -- so a
Windows publish path that is entirely dead FAILS instead of passing on the ubuntu leg's asset").
Once OBS-05 lands, the producer becomes knowable per leg again and this scan can tighten back to
an exact expectation. The surfaced `producerOs` in the log line is what a Phase 10 executor will
read to confirm the tightening is correct.

**An OS-discriminator collapse WITHIN a single run -- a CORR-01 regression in `releaseAssetName`.**
A Windows reader that resolves the ubuntu leg's asset now passes. Two reasons that is tolerable:

- Under today's shared run-scoped seed key the collapse signal is **INSEPARABLE** from the false
  alarm being fixed. Both legs mirror the same linux-produced bytes, so the Windows leg's old-guard
  failure IS the collapse signal AND IS the false alarm -- one cannot be kept without the other.
  OBS-05's leg-distinguishable seeds are what separate them again.
- It stays unit-pinned elsewhere: `release-asset-name.spec.ts` pins the exact produced name, and
  `releases-backend.spec.ts:103-118` is CORR-01's documented non-vacuity proof (named as such in
  ROADMAP Phase 10 item 2, which also schedules its CORR-02 replacement).

Note the retained hypothesis in the new failure message -- "an asset-name discriminator colliding
across RUNS" -- stays accurate: cross-RUN collision is still caught (the hash differs). Only the
within-run cross-OS case is lost. Do not widen that sentence to imply otherwise.

Also no longer caught: a payload whose `producerOs` field was tampered from `linux` to `windows`
while remaining a well-formed dogfood body. Accepted: the payload is generated by our own action
from a fixed template (`dogfood-body.ts:41`), the asset is written by the same run, and the
milestone's threat model does not treat our own publish step as an adversary.

### The asymmetry that must be comment-locked

| Guard | Asserts | Correct because |
|---|---|---|
| `dogfood-verify` (09-05, `action/index.ts:329`) | the LITERAL `'linux'` | `dogfood-seed` is SINGLE-LEG ubuntu by design (`ci.yml:799`), pinned by `dogfood-cross-os.spec.ts:97` whose failure message spells out that a Windows seed leg makes VER-06 vacuous. Producer is known BY CONSTRUCTION. |
| `read-back` (this plan) | any member of `CACHE_OS_VALUES`, and names which | it reads a MIRRORED asset, and `publish` is a TWO-leg matrix sharing one run-scoped seed key. Producer is genuinely VARIABLE. |

Do NOT unify them. Unifying downward (read-back asserts `'linux'`) reintroduces this exact
regression the moment the ubuntu leg loses the `max-parallel: 1` race. Unifying upward
(`dogfood-verify` accepts any OS) destroys VER-06's provenance proof, which is the phase's
headline live closure. The comment lock in `read-back.ts` must say both directions.
</design>
