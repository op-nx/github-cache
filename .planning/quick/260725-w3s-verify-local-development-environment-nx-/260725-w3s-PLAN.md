<pre_flight>
Two decisions this plan makes explicitly, so the executor does not re-litigate them mid-run:

**1. Two states are measured, not one.** RESEARCH 4c proves the only true cold-local-cache
recipe (fresh NX_CACHE_DIRECTORY + fresh NX_WORKSPACE_DATA_DIRECTORY) CHANGES the task hash
under test, and RESEARCH 4b proves there is no recipe that cold-starts only the artifact cache
while preserving the warm-graph hash. Picking one state silently would answer a different
question than the one asked. So:

| State | Recipe | Question it answers |
|---|---|---|
| COLD | fresh NX_CACHE_DIRECTORY + fresh NX_WORKSPACE_DATA_DIRECTORY | What a NEW developer, a fresh clone, and every CI runner actually experience. |
| WARM-GRAPH | a COPY of the real `.nx/workspace-data` + fresh NX_CACHE_DIRECTORY | Whether the hash an established local box computes is the hash CI published. |

WARM-GRAPH deliberately combines a warm graph with a cold ARTIFACT cache, so the local lookup
misses and the remote reader is actually consulted for the warm hash. Known risk: the copied DB
still holds `cache_outputs` rows for those hashes, so Nx may report `[local cache]` even with an
empty artifact dir. If that happens for a task, the remote was never consulted for it -- record
that verbatim as INCONCLUSIVE for that task and rely on Task 3's direct `<hash>-<os>` asset
probe of the warm hash, which answers the same question without Nx. Do NOT edit the copied DB
to force a miss, and do NOT re-run against the real `.nx/`.

**2. The outcome label is NOT this plan's to decide.** CONTEXT.md's UNRESOLVED item stands.
The expected result is all-MISS for reasons already evidenced in CONTEXT.md. Report the facts,
present both readings, choose neither. Nothing in `must_haves` requires a hit, and the executor
must not treat all-MISS as a task failure or a deviation.
