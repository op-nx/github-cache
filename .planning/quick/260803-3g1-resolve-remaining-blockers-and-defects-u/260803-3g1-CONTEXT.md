   sequence from a detached worktree.

`start-cache-server/index.js` (that bundle is serve()-reachable only), so editing it cannot drift
the action bundle. `check:action` should still be run from the main tree as a gate.

### U1 UPDATE 2026-08-03T00:44Z -- burned-name hypothesis FALSIFIED by measurement

The research proposed that deleting the immutable release BURNED the `cache-mirror-202608` name
permanently, citing GitHub's documented *"you can delete the tag, but you cannot reuse the same tag
name"*. **Measured and falsified.** A maintainer-authorized draft probe recreated that exact name:

```
POST /repos/op-nx/github-cache/releases  tag_name=cache-mirror-202608  draft=true
-> 201  id 363934183  draft:true  immutable:false
```

The documented reuse ban carries no draft exception, so a successful create under that name
falsifies it outright rather than partially. The probe release was deleted immediately; the only
remaining `cache-mirror` tag is `202607`.

**Consequence for scope:** August is NOT written off, and the blocker is neither a permissions dead
end nor the deferred design incompatibility.

**What remains unexplained, and must NOT be guessed:** why `createRelease` returned 422 on run
`30773689490`. Two candidates survive, and the plan must not assume either:
- **C-TRANSIENT:** a propagation or resurrection-protection window right after the delete. The run
  created the release ~8 minutes after the deletion; the successful probe ran ~41 minutes after.
  Consistent, unproven.
- **C-NONDRAFT:** something specific to the non-draft path, which is what production calls
  (`action/index.ts:104-108` passes no `draft` flag). The probe could not test this shape -- the
  classifier denied it as creating public surface beyond what was authorized.

**This does not change the B1 fix.** B1 is a real defect on its own evidence (an unguarded re-GET
behind a status-only 422 test), and the fix is what makes the next run NAME its reason instead of
dying anonymously. Both surviving candidates are read off that run, not predicted here.

### ADDITIONAL LOCKED CONSTRAINT from research (Q1)

`uploadFaultCode` as written would NOT name the reason. GitHub's documented `errors[].code` enum
has six members and POLICY rejections arrive as `code: "custom"` with the real diagnostic in
`errors[].message`. A code-only reader prints "code custom" and the next window is spent for
nothing. **The fault reader MUST surface `errors[].message` as well as `code`.** Redact nothing but
tokens; the message text is the payload.
