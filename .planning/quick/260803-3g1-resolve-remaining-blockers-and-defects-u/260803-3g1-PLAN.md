## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub REST 422 body -> CI job log | Attacker-influencable? No -- the body is authored by GitHub, but it IS newly printed verbatim. |
| Actions cache REST response -> o3-witness shell | Server-controlled JSON reaching a `set -euo pipefail` shell that interpolates values into log lines. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3g1-01 | Information disclosure | `faultReason` -> `core.error` / `core.warning` in publish-mirror.ts | low | mitigate | Only `response.data.errors[].code`, `errors[].message` and `data.message` are read. Headers, request config and the Authorization header are never touched, so no token can reach the log. The asset name, the numeric status and GitHub's own validation text are the entire payload. |
| T-3g1-02 | Information disclosure | new `matched_ref` echo in the o3-witness OK line | low | accept | A cache entry's `.ref` is a ref name already visible in the run context; printing it discloses nothing the log does not already carry. |
| T-3g1-03 | Elevation of privilege | o3-witness caches query widened by dropping `&ref=` | low | mitigate | The widening is SERVER-side only in what it RETURNS -- the token's own read scope is unchanged and no permission is added (`actions: read` stays as-is). The accepted set is then narrowed client-side by an explicit two-entry allowlist, so an unrelated ref's entry can never satisfy the witness. |
| T-3g1-04 | Tampering | dependency surface | n/a | accept | No package-manager install task exists in this plan; no dependency is added, removed or bumped. The Package Legitimacy Gate does not apply. |
