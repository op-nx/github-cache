### WR-02: An `errors[]` entry carrying a diagnostic `message` but no string `code` silently loses that message

**File:** `packages/github-cache/src/publish/publish-mirror.ts:159-170`

**Issue:** `entry` is bound only when the candidate has a **string `code`**. When
`errors[0]` is `{ resource: 'Release', field: 'tag_name', message: 'Blocked by org policy X' }`
-- a message with no code -- `entry` is `undefined`, so `entry?.message` is `undefined` and
the reader falls back to `data.message`, which is the generic `"Validation Failed"`. The
one useful string in the body is discarded. This is precisely the outcome the CONTEXT block
calls out as unacceptable ("A code-only reader prints 'code custom' and the next
investigation window buys nothing"), reached through a different door: a code-keyed reader
on a code-less entry.

The `message` extraction does not need to be coupled to the `code` extraction -- they are
independent facts about the body.

**Fix:**
```ts
function faultReason(error: unknown): FaultReason {
  const data = (error as FaultBody | null)?.response?.data;
  const errors = Array.isArray(data?.errors) ? data.errors : [];

  return {
    code: errors
      .map((e) => stringOrUndefined((e as { code?: unknown } | null)?.code))
      .find((code) => code !== undefined),
    message:
      errors
        .map((e) => stringOrUndefined((e as { message?: unknown } | null)?.message))
        .find((message) => message !== undefined) ??
      stringOrUndefined(data?.message),
  };
}
```
The `code` half is unchanged in behaviour; the `message` half now finds the first readable
message anywhere in `errors[]` before falling back.

### WR-03: A matching cache row with a null or absent `created_at` deterministically wins `sort_by` and produces a FALSE "the entry never existed" failure

**File:** `.github/workflows/ci.yml:1241-1245`

**Issue:** MEASURED against jq 1.8.1. `sort_by(.created_at)` places a `null`
`created_at` first, so `first` selects that row even when a perfectly good row with a real
timestamp also matches:

```
input : [{key,ref:"refs/heads/main"}, {key,ref:"refs/pull/16/merge",created_at:"2026-07-05T10:00:00.000Z"}]
result: created=[]  matched_ref=[refs/heads/main]  -> WITNESS FAILS (exit 1 path)
```

The job then prints "no cache entry whose key is EXACTLY ... the entry never existed", which
is false -- one did, and jq had it in hand. `created_at` carries no `required` marker in the
Actions cache-list schema, so this is not impossible, merely unlikely. It is not a
regression in kind (the old `first(... | .created_at) // empty` had the same hole), but the
new `sort_by` makes the bad row win *deterministically* rather than by API ordering.

**Fix:** exclude timeless rows before sorting, so the lower bound is always taken from a row
that actually carries one:
```jq
[.actions_caches[] | select(.key == $key and (.created_at | type) == "string" and (.ref == $ref or ($baseref != "" and .ref == $baseref)))] | sort_by(.created_at) | first // empty
```

### WR-05: The caches request is unpaginated and has no `actions_caches`-is-an-array guard, so an API error payload kills the step with a raw jq error

**File:** `.github/workflows/ci.yml:1238-1241`

**Issue:** MEASURED under `set -euo pipefail`. An error payload from the caches endpoint
(`{"message":"Not Found"}` on a permissions fault, `{"message":"API rate limit exceeded"}`,
or any non-JSON body) makes `.actions_caches[]` fail:

```

jq: parse error: Invalid numeric literal at line 1, column 4  -> subshell exit=5
```

The step dies with no `o3-witness:` message at all. Thirty lines below, the jobs-API block
guards this exact case explicitly and its comment says the guard "is not defensive noise:
without it an error payload ... arrives at the absent-step message -- reintroducing exactly
the wrong-cause report this block was just corrected for" (ci.yml:1278-1281). The caches
call has the same exposure and none of the protection, and the same block also walks pages

The new comment's claim that truncation "fails LOUD rather than passing" is true but
incomplete: it fails with the *misattributing* message at :1245 ("the entry never existed"),

**Fix:** mirror the sibling's guard verbatim, before the select:
```bash

  echo "o3-witness: FAIL -- the caches API returned no \`actions_caches\` array. This is an API, rate-limit or permissions fault, NOT evidence about the entry." >&2

fi
entry=$(printf '%s' "${body}" | jq -c --arg key ... )
```

### WR-06: The allowlist and its FAIL message claim to cover "any ref this run can read" but omit the default branch when it is not the PR base

**File:** `.github/workflows/ci.yml:1196-1199`, `:1210-1214`, `:1245`

**Issue:** A workflow run can restore caches from three scopes: its own ref, the PR base
branch, and the repository default branch. The allowlist admits only the first two, and the
FAIL message asserts the stronger claim:

> "no cache entry whose key is EXACTLY ${key} on any ref this run can read (own ref ..., base ref '...')"

For a PR whose base is not the default branch, an entry in the default-branch scope is
readable by the run, satisfies the witness's actual question, and is rejected by the
allowlist -- producing exactly the Case-B false FAIL this commit exists to remove, one
configuration over. Latent today because every PR in this repo targets `main`, which is the
default branch; the message is nonetheless already inaccurate.

**Fix:** add the default branch as a third allowlist slot and make the message honest:
```bash
default_ref="refs/heads/${GITHUB_DEFAULT_BRANCH:-}"   # or hardcode refs/heads/main with a comment
... select(.key == $key and (.ref == $ref or ($baseref != "" and .ref == $baseref)
                             or ($defaultref != "refs/heads/" and .ref == $defaultref)))
```
If the third slot is deliberately declined, say so in the message: change "on any ref this
run can read" to "on this run's own ref or its base ref".

### WR-09: The class fix's observability half stops at the module boundary; `faultReason` is a second private fault-discrimination contract of the kind `statusOf` was hoisted to `lib/` to prevent

**File:** `packages/github-cache/src/publish/publish-mirror.ts:156`,
`packages/github-cache/src/cleanup/cleanup.ts:146-148`

**Issue:** Two related problems.

1. `faultReason` is module-private to `publish-mirror.ts`. The SUMMARY's
   `patterns-established` claims "One body reader per fault class, shared by **every call
   site of that class**" -- it is shared by the two sites *inside one file*. Sites 4, 5, 6
   and 7 of the same sweep table live in other modules and cannot reach it.
2. The consequence is already visible. `cleanup.ts:147` renders
   `failed to delete ${asset.name} (status ${statusOf(error) ?? 'unknown'})` -- status only,
   no code, no message. B2's whole finding is that a **code-only** reader is useless; a
   status-only one is strictly weaker than that. The same body is available on a cleanup
   fault as on a publish fault.

`octokit-status.ts:6-12` documents exactly why this matters: `statusOf` was extracted into
`lib/` because the 404/422/5xx contract "was previously authored byte-identically in both
(I8/simplify: drift risk on a fault-discrimination contract encoded twice)". `faultReason`
recreates that risk one layer up, in the same subsystem, in the commit that cites the
lesson.

**Fix:** move `faultReason`, `FaultBody`, `FaultReason` and `stringOrUndefined` into
`src/lib/octokit-status.ts` (or a sibling `octokit-fault-reason.ts` leaf), export them, and
have `cleanup.ts:146-148` render `code`/`message` on the same footing:
```ts
const reason = faultReason(error);
core.warning(
  `github-cache cleanup: failed to delete ${asset.name} (status ${statusOf(error) ?? 'unknown'}, code ${reason.code ?? 'unknown'}, message ${reason.message ?? 'unknown'}); continuing.`,
);
```
This is a pure observability change; it touches no branch and no counter, so it does not
reopen the deliberate `cleanup.ts:137` deferral.

### IN-01: `cleanup.ts:137`'s deferral independently re-derived and CONFIRMED adequate, but justification 2 is now imprecise

**File:** `packages/github-cache/src/cleanup/cleanup.ts:137-143`

The deferral is not the next blocker in disguise. Re-derived:

- The benign reading is genuinely the desired end state of a DELETE, and `pruned` stays
  true under it.
- The masked-403-as-404 risk requires an invisible resource. `op-nx/github-cache` is public
  and the asset was just enumerated by the same token, so a scope loss presents as 403 (ends
  in `failed++`, loud), not 404.
- An immutable-release asset DELETE almost certainly answers 422 by analogy with the upload
  path measured in E7 -- also `failed++`, also loud.
- `pruned` gates nothing: it reaches `writeCountSummary` and the return value only. No
  guard or breaker can be defeated by inflating it.

The imprecision: justification 2 says "There is no body to consult. A DELETE 404 carries no
`errors[]` array". A GitHub 404 body does carry `{"message":"Not Found"}`, and as of this
commit `faultReason` reads `data.message`. The *conclusion* survives -- "Not Found" is not a
discriminator, since both a genuine absence and a masked 403 render it -- but the premise as
written is now falsifiable by the code shipped alongside it. Restate as "the body carries no
field that DISCRIMINATES the two readings".

### IN-02: The M4 gap comment overstates how tightly the gap is bounded

**File:** `packages/github-cache/src/dogfood-cross-os.spec.ts:648-651`

The comment says "The gap is `[^\n]*\n`, ONE line". The regex is
`/if \[ -z "\$\{created\}" \]; then\n[^\n]*\n\s*exit 1\n/`, and `\s` matches `\n`, so the
trailing `\s*` also spans blank lines. Harmless -- only whitespace can be skipped, so no
distant `exit 1` is reachable, which I confirmed by mutation -- but the comment claims a
tighter bound than the regex has. Say "one arbitrary line plus any blank lines".

### IN-04: The `already_exists` acceptance reads only the first string-coded entry and ignores `field`

**File:** `packages/github-cache/src/publish/publish-mirror.ts:159-167`, `:212`

Two narrow observations, neither currently exploitable:

- `faultReason` returns the code of the FIRST entry carrying a string `code`. A body shaped
