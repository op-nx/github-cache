## Task 1 -- the createRelease 422 classifier (B1 + B2)

`ensureShardRelease` treated ANY 422 as "another matrix leg won the create race" and re-GET the
shard unguarded. Both halves were wrong, and run `30773689490` is the falsifying measurement:
after the run there was no `cache-mirror-202608` release, no such tag ref (exit 1, with
`cache-mirror-202607` as a passing positive control) and no draft. A 422 cannot mean
`already_exists` when the resource provably does not exist.

What changed:

- the create-catch requires an EXPLICIT `already_exists` before taking the race path;
- the re-GET is wrapped even on a genuine race and rethrows an error NAMING the tag and the
  re-read status, with the original as `cause`;
- every other 422 `core.error`s ONE line carrying the tag, the status, GitHub's code and GitHub's
  message, then rethrows the original error (so `statusOf` stays readable downstream);
- `uploadFaultCode` is renamed `faultReason`, widened to `{ code, message }`, and now serves BOTH
  422 sites. The upload warning carries the message too.

The message is the load-bearing half of B2. GitHub's `errors[].code` enum is GLOBAL and
six-membered; policy rejections (rulesets, immutability, org settings) arrive as `custom`, whose
documented meaning is literally "refer to the message property to diagnose the error". A code-only
reader prints `code custom` and the next investigation window buys nothing.

### `cleanup.ts:137` -- assessed, FLAGGED, and deliberately not fixed

It is the ONE surviving site whose wrong reading is silent GREEN rather than a loud fault. If the
token's delete capability regressed and GitHub answered 404-instead-of-403, cleanup would count
every asset as `pruned` and exit 0 having deleted nothing -- structurally the same shape as the
publish bug, one subsystem over.

Why it is nonetheless SAFE as written, and why it is not fixed here:

1. **The benign reading is the DESIRED END STATE of a DELETE.** A DELETE whose target is absent is
   idempotently successful, and `pruned` means "N assets are now gone", which stays true.
2. **There is no body to consult.** A DELETE 404 carries no `errors[]` array, so the fix that
   closed sites 2 and 3 -- read the code, require an explicit one -- has no analogue here. Any fix
   would be a different mechanism (an outcome-shape tripwire), not this task's.
3. **The risk is INFERRED and unmeasured.** The workflow declares `contents: write`, and a real
   scope loss is more likely to surface as 403 than as a masked 404.
4. **Fixing it here would repeat `e96670e`'s error in the opposite direction** -- shipping an
   unmeasured change to a second subsystem inside a commit whose whole purpose is to make the
   FIRST one measurable. The correct next step is a measurement, not a patch.

The cheap tripwire when it is wanted: "every expired asset resolved via the 404 path and none via
a 2xx" -- an all-404 delete batch, the cleanup analogue of the all-restore-MISS warning
`publish-mirror.ts` already implements.

## Task 2 -- o3-witness Case-B safety without vacuity (D1)

The witness asserted `.ref == $GITHUB_REF`, which encodes the Case-A shape (producers MISS, SAVE,
the entry lands on this run's own ref). On run `30768540898` every ubuntu producer HIT, nothing was
written to the PR merge ref, and the entry the Windows legs restored lives in the DEFAULT-branch
scope -- so the equality found nothing and the job reported "the entry may never have existed"
about an entry that does exist.

Both halves shipped together, because widening the jq alone would have been inert: a server-side
`&ref=` narrow can only ever RETURN rows on the ref being asked about. The parameter is dropped
from the URL and the ref constraint moves client-side as an ALLOWLIST (own ref OR a non-empty base
ref). It is never dropped -- one hash holds entries on two refs, so a key-only match is not an
existence proof.

### M4 -- the mutation, and the defect the mutation found in the clause itself

M4 is not naturally RED: the empty-result branch already exits 1. Proven by MUTATION -- `exit 1`
temporarily changed to `exit 0` in that branch.

**The first attempt at the clause was VACUOUS, and the mutation is the only reason that is known.**
Written as the research proposed:

```js
.toMatch(/if \[ -z "\$\{created\}" \]; then[\s\S]*?exit 1/);
```

the mutated workflow ran **71 passed (71)** -- fully GREEN. Non-greedy bounds how much the gap
PREFERS to consume, not how far it MAY reach: with the branch's own `exit 1` mutated away, the gap
simply walked past the closing `fi` and matched the jobs-API `exit 1` a hundred lines further down.
A structural guard that can satisfy itself from an unrelated part of the same block is not a guard.

The clause was rewritten to bound the gap to the branch's single message line AND to forbid

### The jq expression was probed directly, not merely pinned

A green structural guard can sit over a wrong payload, so the filter was run against fixtures with
jq 1.8.1 before landing (probe script written to the session scratchpad, never to the repo):

| Case | `created` | `matched_ref` |
|------|-----------|---------------|
| own-ref hit (PR merge ref, base also holds an older copy) | `2026-07-01T10:00:00.000Z` | `refs/heads/main` |
| base-ref only (Case B) | `2026-07-01T10:00:00.000Z` | `refs/heads/main` |
| push, no base ref | `2026-07-01T10:00:00.000Z` | `refs/heads/main` |
| unrelated ref only, no base ref | *(empty)* | *(empty)* |
| a row whose `.ref` is the empty string, base ref empty | *(empty)* | *(empty)* |
| empty `actions_caches` array | *(empty)* | *(empty)* |
| key that is only a PREFIX of the requested key | *(empty)* | *(empty)* |

All three negative cases yield an empty string, never a foreign row and never the literal `null`.
The empty-`.ref` case is what proves the `$baseref != ""` guard is load-bearing: without it an
entry with no ref would satisfy an empty allowlist slot.

**One overclaim corrected from the plan's own wording.** Because the EARLIEST readable copy is
selected, a Case-A run whose base branch also holds an older copy prints the BASE ref. So
`matched_ref` is the provenance of the LOWER BOUND, not a claim about which run created the entry.
Both the `ci.yml` comment and the spec's reason string say exactly that rather than the tidier but
false "Case A versus Case B" reading -- planting a false comment is the CRITICAL this project has
already shipped once.
