## Summary

The five decisions (D1 seed filter, D2 `bead` marker word, D3 pre-restore membership
skip, D4 metric split, D5 partial-miss guard) are implemented and the three locked
security constraints hold. I verified each of the latter directly rather than taking the
commit bodies' word for it:

- **C2 (`actions: write` unrequested)** -- the diff adds no `permissions:` block and
  changes none. The only `actions:` grants in `ci.yml` remain the two `actions: read`
  entries (o3-witness, publish). T-11-01's absence-mitigation is intact.
- **C3 (`listCacheEntries` `ref` scoping)** -- `createPublishClient` is untouched apart
  from the added `{ runId }` argument at the `publishMirror` call site. The `ref`
  positional and its comment lock are byte-identical. TRUST-10 / C1 / C2 / C16 intact.
- **C1 (current run's seed still mirrored at every feed index)** -- the admission rule is
  marker-prefix AND `!endsWith(runId)`, so every `cafe<run>` / `bead<run>` / `feed<i><run>`
  key of the *current* run is admitted regardless of index or family. `publish-verify`
  cannot be starved by the filter. The residual errs only toward admitting.
- **Loop reconciliation** -- I traced all ten `continue`/terminal paths: every iteration
  increments exactly one of `mirrored` / `skipped` / `failed`, and `readMisses` /
  `alreadyPresent` are disjoint strict subsets of `skipped`. `scanned` reconciles.
- **Fail-open path** -- `isOtherRunsSeed` returns `false` for `undefined` and `''`, and
  `runPublish`'s forwarding is pinned on the exact value, not on presence. The D1
  describe's exact-array assertions would redden if the predicate inverted or the marker
  list emptied. `runId` reaches only `startsWith`/`endsWith` -- no regex construction, no
  path or command interpolation, so the new untrusted-looking input is not an injection
  surface.
- **D5 boundary arithmetic** -- `readMisses >= hashes.length * 0.5` with the `else if`
  ordering; the total case is arithmetically subsumed and reaches its own message first.
  No division by zero is reachable (`readMisses > 0` implies `hashes.length > 0`).

**No blocker found.** What I did find clusters almost entirely in the review directive's
category 2 -- *prose that is false*. Five separate comments in this diff assert
constraints or purposes the code does not have, and one shipped assertion cannot fail
independently of the two above it. In a repo whose stated defence against stale claims is
comment locks and phrase specs, a comment that invents a constraint is not cosmetic: two
of these (WR-01, WR-03) actively mislead the next reader into either preserving dead
structure or deleting live structure.

## Warnings

### WR-01: The D1 filter's "position before the `Set` is load-bearing" claim is false

**File:** `packages/github-cache/src/publish/publish-mirror.ts:427-434` (also
`.planning/.../260809-2s6-PLAN.md` key_links, and the RESEARCH pitfall it cites)
**Issue:** The comment states the filter's position inside the pipeline is load-bearing:
"BEFORE the `Set`, so a filtered seed can never inflate the distinct-hash count that the
all-MISS gate below reads."

`isOtherRunsSeed` is a pure predicate over the element value, and `Set` dedups by value.
`new Set(xs.filter(p))` and `[...new Set(xs)].filter(p)` therefore produce an identical
array, in identical first-occurrence order. A filtered seed is removed in both orders and
can inflate nothing in either. The claimed constraint does not exist.

This matters because the plan promoted it to a `key_links` invariant, so a future reader
who needs to reorder the pipeline (for example to filter on the entry key rather than on
the parsed hash) will believe they are breaking the all-MISS gate and will not.
**Fix:** Keep the current position -- it is the right place to read -- but state the real
reason and drop the invented one:

```ts
// D1. Placed inside this pipeline as a SECOND, narrowing filter rather than as an edit
// to isServerProducedKey or HASH_PATTERN -- those predicates are shared with the
// server's SRV-03 route and both cleanup branches, their literal count is
// comment-locked, and `cache-key.ts` is a leaf with no notion of a run (it is also in
// the action bundle, which this file is not). Position relative to the `Set` is a
// readability choice, NOT an invariant: the predicate is pure and dedup commutes with
// it, so filtering after the Set yields the identical array.
```

### WR-02: The exported threshold's stated purpose is contradicted by its only consumer

**File:** `packages/github-cache/src/publish/publish-mirror.ts:38-41`
**Issue:** `PARTIAL_READ_MISS_WARN_RATIO`'s docblock says it is "Exported so a spec can
drive the boundary from the constant rather than from a literal that would drift from
it." No spec does that. `publish-mirror.spec.ts:1265-1278` pins the constant to the
literal `0.5`, and the three boundary cases hardcode a 4-entry enumeration with 2 and 1
misses. The spec's own comment concedes it: "Changing the ratio invalidates those fixtures
rather than merely moving them, so it must be changed HERE and in them together."

So the export buys a value-pin, not a derived boundary -- the exact thing the docblock
says it exists to avoid.
**Fix:** Either make it true, by deriving the fixtures:

```ts
const TOTAL = 4;
const AT_THRESHOLD = Math.ceil(TOTAL * PARTIAL_READ_MISS_WARN_RATIO);
// ...mock AT_THRESHOLD misses for the warn case, AT_THRESHOLD - 1 for the silent case
```

or correct the docblock to say what the export actually is: "Exported so a spec can PIN
the value; the boundary fixtures are hand-built for one half and must move with it."

### WR-03: "the cap branch is now reached only by names that are ABSENT" is false, and the comment invites deleting a live guard

**File:** `packages/github-cache/src/publish/publish-mirror.ts:517-519` (branch at 594)
**Issue:** The D3 comment claims the D-11 asset-cap branch "is now reached only by names
that are ABSENT, which is behaviourally identical because that branch already exempts
present names."

The first entry of a run falsifies this. On iteration 1 `shard` is `undefined`, so the
pre-restore membership guard is skipped by construction; the restore then resolves the
shard, and control reaches the cap branch with a name that may well be present -- which is
precisely the case the surviving post-restore first-write-wins branch exists to catch (and
which the file documents 100 lines lower as "STILL REACHABLE AFTER D3").

The `!shard.names.has(name)` clause in the cap condition is therefore still load-bearing.
A reader acting on this comment would delete it as dead, and a shard at the 1000-asset cap
would then emit a spurious cap warning for an entry that is already mirrored, and count it
as a plain `skipped` rather than an `alreadyPresent`.
**Fix:**

```ts
// The D-11 cap branch below is now reached with a PRESENT name only on the FIRST entry
// of a run -- the one that resolves the shard, and so the one the pre-restore guard
// could not test. Its `!shard.names.has(name)` clause is still load-bearing for exactly
// that entry; do not delete it as newly-dead.
```

### WR-04: The third dogfood assertion cannot fail independently, and its comment says otherwise

**File:** `packages/github-cache/src/dogfood-cross-os.spec.ts:113-152`
**Issue:** The case asserts, in order:

```ts
expect(seed, reason).toBe('bead${{ github.run_id }}');
expect(verify, reason).toBe('bead${{ github.run_id }}');
expect(seed, reason).toBe(verify);
```

The third is entailed by the first two -- if both equal the same literal they equal each
other, so `toBe(verify)` can never be the first failing assertion. Deleting it changes
nothing the gate detects. The comment above it, however, states "THREE CLAUSES, and each
closes a hole the other two leave open," then attributes to the equality clause a hole
(both jobs reverted together) that the two literal pins already close on their own.

This is the review's category-1 test: *would deleting the guarded text pass?* For clause 3,
yes. The framing is correct as a description of three weaker *alternative designs* that
were rejected; it is wrong as a description of the three assertions actually shipped.
**Fix:** Keep all three lines if the redundancy is wanted as documentation, but relabel it
honestly -- or make the equality clause independently load-bearing by pinning the shape
rather than the whole literal:

```ts
const SHAPE = /^bead\$\{\{\s*github\.run_id\s*\}\}$/;
expect(seed, reason).toMatch(SHAPE);   // marker + run id, nothing else
expect(verify, reason).toMatch(SHAPE);
expect(seed, reason).toBe(verify);      // now genuinely independent: two distinct
                                        // run-id expressions would satisfy SHAPE twice
```

### WR-05: `scanned`'s field documentation was not updated for D1

**File:** `packages/github-cache/src/publish/publish-mirror.ts:97-103`
**Issue:** `scanned` is documented as "DISTINCT server-produced hashes enumerated
(listCacheEntries returns one row per (key, version) and the rows are deduped below, so a
key saved under two archive versions counts once). The denominator the other counts are
read against." After D1 it is *enumerated, deduped, and minus every other run's seed* --
the inline filter comment is emphatic that this shrinks the number and that pre-fix figures

This field doc is the canonical explanation of the OBS-01 denominator and the one a reader
of the job summary will reach for; leaving it describing the pre-D1 meaning re-creates the

**Fix:** Add one clause to the field doc: "...counts once), MINUS any single-use CI seed
belonging to another run (D1, see `isOtherRunsSeed`). Figures recorded before that filter
are not comparable to these."

### WR-07: D3 has a third aggregate consequence that the commit body claims it enumerated exhaustively

**File:** `packages/github-cache/src/publish/publish-mirror.ts:501-538`; commit `3cdf87c`
body ("TWO AGGREGATE OUTCOMES CHANGE, and review should not have to discover them")
**Issue:** Before D3 the publish legs restored *every* enumerated entry on every
default-branch push, which is an access against the Actions cache and therefore refreshed
GitHub's 7-day-unaccessed eviction clock for every mirrored entry. After D3, entries whose
asset name is already in the shard are never restored, so publish no longer refreshes them.

Impact is bounded and probably benign -- a task hash still in use is fetched by the sidecar
on each run and refreshed that way, and an entry already mirrored is readable from the
Release shard through the shard-window walk until retention prunes it. But it is a real,
unstated change in the effective lifetime of an Actions-cache entry, and it interacts with
the month-shard rollover: a hash that has evicted from the Actions cache cannot be
re-mirrored into the next month's shard, where previously publish's own restore kept it
alive indefinitely.

`ci.yml:1942` already names the 7-day-unaccessed policy, so the mechanism is known to the
repo; the change to it is not recorded anywhere.
**Fix:** Add it as the third bullet in the D3 comment's "TWO AGGREGATE OUTCOMES CHANGE"
paragraph (and rename the paragraph), stating the mechanism, why it is accepted, and the
one case worth watching -- a hash that evicts before the month rolls over is not
re-mirrored into the new shard.

### WR-08: T-2S6-01's "structural" mitigation rests on an externally-owned property nothing pins

**File:** `packages/github-cache/src/publish/publish-mirror.ts:147-166`,
`packages/github-cache/src/lib/mirror-seed.ts:44-51`, `.github/workflows/ci.yml:2462-2473`
**Issue:** The filter is safe in the C1-forbidden direction only because a real Nx task
hash cannot begin with `cafe` / `bead` / `feed`, which holds only because Nx renders task
hashes as decimal. I confirmed that empirically for the pinned toolchain -- Nx 23.1.0, and
every entry under this workspace's `.nx/cache` is an all-decimal u64 -- so the property is
true today.

What is missing is that nothing in the repo fails if it stops being true. The evidence
cited in `ci.yml` is itself empirical ("verified over 153 local cache entries, zero
containing a-f"), yet all three sites call the resulting disjointness STRUCTURAL, and the
plan's threat register dispositions T-2S6-01 as mitigated on that basis. Before D1 a
violation cost a cosmetic collision in a shard listing; after D1 it costs the entry being
silently dropped from the mirror -- no error, no red, just a consumer cache MISS forever
for that hash. The consequence of the assumption failing was upgraded by this change; its
verification was not.
**Fix:** Either downgrade the wording (the disjointness is *empirical over the pinned Nx*,
not structural, and the pin is what carries it), or add the cheap gate that makes an Nx
upgrade surface it -- e.g. a spec over the local `.nx/cache` entry names asserting none
carries a hex letter, run as a non-blocking canary, with the Nx version named in the
failure message.

### WR-11: D5's stated division of labour credits a gate the named cause cannot trip

**File:** `packages/github-cache/src/publish/publish-mirror.ts:715-735`; plan must_have
"the total case remains covered by the existing gate (D5)"
**Issue:** The total-case gate requires `readMisses === hashes.length && mirrored === 0`.
On the publish legs `mirrored === 0` is effectively unreachable for the cause the gate
names: `ci.yml` runs the `mirror-seed` step immediately before the `publish` step in the
same job, so this leg's own `feed<i><run_id>` seed is written in this run, under the
current cache version, on the default-branch ref -- it is enumerated and it always
restores. A cache-VERSION rotation therefore leaves `mirrored >= 1` and the total gate
silent; only a read-scope regression severe enough to hide the seed itself can reach it.

The practical outcome is fine, and arguably better than documented -- a rotation will now
trip the new partial guard at ~100% minus the seeds. But the comment (and the plan's
must_have) presents the two branches as covering the total and partial cases respectively,
when in this workflow the partial branch is the live signal for both. A reader tuning the
threshold later will over-weight a gate that does not fire.
**Fix:** Add one sentence to the partial branch's comment: "In THIS workflow the gate above
is effectively unreachable on a version rotation -- the leg writes its own mirror-seed in
the same job, so that seed always restores and `mirrored >= 1`. Treat this branch as the
live rotation signal; the gate above covers only a read-scope regression wide enough to
hide the seed."

## Info

### IN-01: No invariant assertion on the count reconciliation

**File:** `packages/github-cache/src/publish/publish-mirror.spec.ts`
**Issue:** The reconciliation the D4 split is required to preserve --
`mirrored + skipped + failed === scanned`, and `readMisses + alreadyPresent <= skipped` --
is asserted only implicitly, case by case, through eleven whole-result `toEqual`s. A new
`continue` path that forgot to increment (or that incremented two counters) would be caught
only if someone also wrote a case for it.
**Fix:** One cheap invariant helper applied in the existing cases, or a single case over a
mixed fixture asserting both relations directly.

### IN-02: The `cafe` marker literal is pinned on only one side

**File:** `.github/workflows/ci.yml:2137`, `packages/github-cache/src/publish/publish-mirror.ts:166`
**Issue:** `bead` is now pinned on both sides (the ci.yml literal by the new dogfood case,
the array entry by the D1 exact-array case), and `feed` is pinned by `mirror-seed.spec.ts`.
`RUN_HASH: cafe${{ github.run_id }}` is pinned by nothing, so consumer-smoke's marker can be
renamed with the whole suite green. Drift is fail-open as documented, so this is a
consistency gap rather than a fault -- but the array comment presents all three literals as
equally unguarded, which understates two of them and overstates this one.
**Fix:** Either add the one-line ci.yml pin for symmetry, or note in the array comment which
of the three are independently pinned and which is not.

### IN-03: The partial guard has no minimum-denominator floor

**File:** `packages/github-cache/src/publish/publish-mirror.ts:715-718`
**Issue:** `readMisses >= hashes.length * 0.5` fires at one miss out of two. Unreachable at
this repo's ~100-entry denominators, but a fresh cache scope or a heavily-filtered
enumeration would warn on a single miss -- and the branch's own rationale is that a
tripwire firing on correct work gets disabled.
**Fix:** If it ever proves noisy, gate on a small absolute floor as well
(`hashes.length >= 8 && ...`); recording the omission as deliberate is enough for now.
