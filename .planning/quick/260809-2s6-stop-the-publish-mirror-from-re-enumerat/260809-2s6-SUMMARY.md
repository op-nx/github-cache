# Quick Task 260809-2s6: Stop the publish mirror from re-enumerating prior runs' seeds -- Summary

Structural seed filter plus a split OBS-01 metric: the publish mirror no longer
restores prior runs' single-use CI seeds, no longer round-trips entries already in
the shard, and no longer reports two different things under one number.

## What Was Built

**Task 1 -- the third marker word (D2).** Commit `46f0b8a`.

`dogfood-seed` and `dogfood-verify` moved from `hash: ${{ github.run_id }}` to
`hash: bead${{ github.run_id }}`. The bare run id is all-decimal, which is exactly
the character class of a real Nx task hash, so this family was the only genuinely
unfilterable one -- and 28 of the 48 stale seed entries belong to it. The marker
word is hex letters, so the key stays inside the server's `^[a-f0-9]{1,512}$`
validator while becoming structurally separable.

The prose that asserted the superseded shape was swept across six sites plus two
in a spec. One of them was not in RESEARCH's list and was found by reading the
job: dogfood-seed's own two-line rationale justified the choice on the ground that
the run id is ALREADY all-decimal and needs no massaging -- a sentence this edit
makes false.

A new spec case pins each job's `hash:` value WHOLE and anchored plus their
equality. Proven non-vacuous by mutation: reverting only `dogfood-verify` reddens
it with a message naming the round-trip.

**Task 2 -- the filter and the reorder (D1, D3).** Commit `3cdf87c`.

`isOtherRunsSeed` answers "is this a seed belonging to some OTHER run" -- true when
the hash begins with one of the three marker words AND does not end with the
current run id. Wired as a second `.filter` in the existing pipeline, after the
`parseHash` narrowing and before the `Set`, so a filtered seed cannot inflate the
distinct-hash count. `runPublish` reads `process.env.GITHUB_RUN_ID` and forwards it
as `PublishOptions.runId`.

Shard membership now runs at the top of the loop, above the restore, guarded on the
lazily-resolved shard being defined.

**Task 3 -- the split metric and the partial guard (D4, D5).** Commit `e78a842`.

`PublishResult.alreadyPresent`, a second strict subset of `skipped`, incremented
from both membership branches and NOT from the duplicate-upload race. A summary row
added; the existing miss row's label untouched. All eleven whole-result assertions
updated with case-correct values.

`PARTIAL_READ_MISS_WARN_RATIO = 0.5` and a second warning branch written as an
`else if` on the existing total-case branch.

## NOT OBSERVED

Two things this task cannot confirm locally, recorded as NOT OBSERVED rather than
inferred. `publish` is push-gated to the default branch, so neither is reachable
from a PR run and no live window was opened.

1. **The actual post-fix `readMisses` / `scanned` ratio.** Every figure behind the
   D5 threshold is DERIVED from run `31281406708` plus an assumption about which
   cohort D1 removes. The first live post-fix run on `main` is when the real
   numerator and denominator land, and it is the recorded revisit trigger for the
   threshold. The expectation is that `readMisses` falls toward the real-hash
   cohort plus the unfilterable bare-run-id entries -- but it has not been seen.

2. **Both `publish-verify` legs staying green.** C1 requires every seed of the
   CURRENT run to survive the filter at every feed index, and that is asserted at
   the unit level against an exact restore-call list. Whether the live round-trip
   stays green is a live-CI observation that has not been made.

A third, smaller one: the `bead` round-trip itself. The seed and verify halves are
pinned to the same value by a spec, but the actual cross-job cache HIT under the
new key has only ever run under the old one.

## Deviations from Plan

**1. [Process] One commit per task rather than a RED/GREEN pair.**

The plan marks all three tasks `tdd="true"`, which nominally means a failing-test
commit followed by an implementing commit. The dispatch instruction was "Execute
all 3 tasks in the plan. Commit each atomically", and each task's `<done>`
describes a single end state, so each task landed as one commit. A RED commit for
Task 1 would have left the ci.yml gates failing at HEAD, and for Tasks 2 and 3 the
whole package suite. The RED direction was verified by MUTATION instead -- applied,
observed red, reverted -- which produces the same evidence without a red HEAD. No
`test(...)`-then-`feat(...)` gate pair exists in the log for this task; recorded
here rather than left for a TDD-gate scan to find.

**2. [Rule 2 - Correctness] The `alreadyPresent` value was per-case, and only ONE
of the eleven is non-zero.**

The plan warned against blanket-adding a zero because "several of those cases
exercise the already-present path". Measured: exactly one does -- the first-write-wins
pre-list case. That case now carries `alreadyPresent: 1` and a comment saying it is
the only one, so a future blanket edit is visibly wrong rather than silently so. The
plan's "several" is the only figure in it that did not survive contact; the
instruction it supported was still the right instruction.

**3. [Scope] `10-VERIFICATION.md`'s stale `readMisses 0` expectation was NOT
corrected.**

CONTEXT.md's canonical-refs section says L3's `expected` "still says `readMisses 0`
and must be corrected to the post-fix steady state as part of this task". No task in
the PLAN covers it, the dispatch forbids committing planning artifacts, and the
correct post-fix value is precisely the thing item 1 above records as NOT OBSERVED
-- so correcting it now would replace one unverified expectation with another. Left
for the live post-fix run, which is when the real figure exists.
