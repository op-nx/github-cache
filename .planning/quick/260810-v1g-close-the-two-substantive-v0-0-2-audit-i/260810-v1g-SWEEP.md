## Verdict: 22 of 22 green on all eight gates

All 22 commits in `4518787..1b06816` leave all eight gates green, uncached, on the main checkout. Every
one of the 88 recorded process exit codes is 0, and every one of the 22 `nx` logs carries the
five-target success line exactly once. Cited by `RESULTS.tsv` and the 88 per-gate logs in `LOG_DIR`.

**This supersedes kuo's framing.** `260810-kuo-VERIFICATION.md` and `260810-kuo-SUMMARY.md` left this
open on the grounds that "full per-commit verification is 22 checkouts x 6 gates" and "was not run".
That framing predates any measurement of the battery. Measured here, from the sweep's own file
timestamps: the whole thing, 22 commits x eight gates, ran in **369 seconds -- 6 minutes 9 seconds**
of wall clock end to end, which is about 17 seconds per commit including the checkout. The `nx` phase
printed `Run duration` between 3.6s and 5.9s per commit. There was never a cost reason to stop short
of 22/22, and none was taken.

**No red commit, and no bundle drift.** `check:action` rebuilds `start-cache-server/index.js` with
esbuild and then diffs it, so a commit whose committed bundle disagreed with a fresh build of its own
sources would have failed the gate and left the tree dirty. None did: `action=0` on all 22. That
matters because `start-cache-server/index.js` is untouched by every commit in the range, so drift at a
mid-range commit would have been a genuine finding rather than noise. The unconditional
`git checkout -- start-cache-server/index.js` at the end of every iteration ran after the exit code was
recorded, never before, so it could not have masked a finding.

The sweep was run on the main checkout, never in a worktree, deliberately. A junctioned `node_modules`
makes esbuild rewrite hundreds of module paths with no source edit, so `check:action` in a worktree
returns a false drift verdict. Only the main tree gives a true one.

## One INSTRUMENT finding, and it is in the probe, not in any commit

The in-loop `ran` probe measured 0 on all 22 commits while `nx` exited 0 on all 22. Raw record, from
`RESULTS.tsv`: every row reads `nx=0 ran=0`. Under the rule this sweep was told to follow, `ran=0` with
`nx=0` is the missing-target failure mode and must be treated as RED rather than green, so this had to
be resolved rather than waved past.

Resolved by measurement. This is an INSTRUMENT defect in the probe, cited to `1-a149f9540e3c85d7a9671a2a5c5bed8ffa50791c-nx.log`.
The needle was the plain literal `Successfully ran targets build, typecheck, test, integration, lint`,
but Nx emits each target name wrapped in SGR bold escapes, so the literal cannot match. Verbatim from
that log, escapes rendered visible with `cat -v`:

```
Successfully ran targets ^[[1mbuild^[[22m, ^[[1mtypecheck^[[22m, ^[[1mtest^[[22m, ^[[1mintegration^[[22m, ^[[1mlint^[[22m for project
```

That is the discriminating line: all five targets are named, in order, on the success line, in a log
whose process exit code was 0. A silently deleted target would not produce it.

Recount over the same captured logs, with `sed 's/\x1b\[[0-9;]*m//g'` stripping the escapes before the
same literal needle: 1 hit in each of the 22 `nx` logs, 22 total. Three controls, so the recount is not
self-confirming:

- The unstripped literal matches 0 of the 22 logs, which is what identifies the escapes as the cause
  rather than an absent line.
- The stripped needle with one target dropped from the list (`build, typecheck, test, lint`) matches 0.
  The probe can still fail, so a real missing target would still be caught.
- The stripped needle against a `format.log`, which has no such line, matches 0.

The `ran` column above therefore carries the recounted value. `RESULTS.tsv` preserves the raw `ran=0`
unedited; the discrepancy between the two is this finding, not a correction of the evidence.

## Limit of this document, stated rather than implied

No automated check can prove an INSTRUMENT classification is CORRECT. The only mechanical discriminator
would be re-running the gate until it goes green, which is exactly the pass condition the locked
best-effort decision forbids. What is guaranteed here is falsifiability: the classification above cites
its log by name and quotes the line that distinguishes a broken probe from a broken gate, so a reader
can open `1-a149f9540e3c85d7a9671a2a5c5bed8ffa50791c-nx.log` and disagree. The verify asserts only that
the citation exists.

Two further honest limits. The gate results are Windows-arm64 local measurements on the maintainer's
workstation, not CI runners; nothing here was pushed, and no CI run was created. And `LOG_DIR` is a
session scratchpad path outside the repo, so it is durable for this session and its transcript, not
forever. `RESULTS.tsv`'s 22 rows and this table are the record that survives.
